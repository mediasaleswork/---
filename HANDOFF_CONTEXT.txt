PARTNER MONITOR — КОНТЕКСТ ДЛЯ ПРОДОЛЖЕНИЯ

Пользователь разрабатывает Telegram-юзербота для рекламного агентства. Аккаунт читает доступную рабочую группу, куда ежедневно присылают сообщения и файлы с клиентом, рекламируемым брендом/продуктом/услугой, типом рекламы, каналом и длительностью размещения. Нужно одновременно вести разные заявки, клиентов и посты круглосуточно.

ПРИОРИТЕТЫ И СОГЛАСОВАННЫЕ УСЛОВИЯ
1. При появлении подходящего поста нужен первый настоящий скриншот с видимым счётчиком, ссылка, дата и просмотры API.
2. Вступать в каналы автоматически нельзя. Публичные каналы читаются через доступный Telegram API; закрытая ссылка сама по себе не даёт доступа. В текущей реализации — события NewMessage/Album и поддержание getChannelDifference максимум для 10 публичных каналов без подписки, плюс периодическая история. Точную секунду выхода гарантировать нельзя.
3. Название в заявке — рекламируемый бренд, продукт или услуга. Конкретные BRB/БРБ/brb.uz не должны быть глобальными обязательными признаками. Клиент — отдельное необязательное поле; не приравнивать его автоматически к названию рекламы.
4. Часы размещения — сколько пост должен оставаться в канале после публикации, а не крайний срок выхода. Период публикации задаётся отдельно; без даты по умолчанию 7 дней от сообщения группы, с отметкой в отчёте.
5. Будущая доработка: для поста на 24 часа — повторный снимок через 20 часов после публикации, затем заменить видимый первый снимок новым. Это последнее условие пользователя, уточнившее прежнее «за час до удаления». Для неизвестного срока — повторный снимок через 48 часов. Правило для других длительностей нужно согласовать. Пользователь отложил этот этап до создания/подключения юзербота и сервера.
6. Отложенные задания должны быть индивидуальными для каждого поста и храниться в БД, переживать перезапуски и исполняться независимо от новых заявок. Сейчас отдельной надёжной очереди таких заданий ещё нет; не выдавать замену через 20 часов за готовую функцию.
7. Нужен один удобный Excel-файл: клиент/канал/план/вышло/остаток; реестр постов с фильтрами; статусы; просмотры; встроенные изображения. Удалённый/недоступный пост должен сохранять последнее доказательство. Недоступность API не считается доказанным удалением.

ЧТО СДЕЛАНО
Актуальная версия 0.4.0 находится в project/. Исходный пользовательский ZIP — attachments/partner-monitor.zip. Релизы 0.2, 0.3 и 0.4 и последний макет — deliverables/.
Python 3.11+, Telethon 1.x, Playwright/Chromium, SQLite, openpyxl, Pillow. По последней полной проверке на Windows / Python 3.13.17 прошли 113 тестов, включая 4 браузерных теста на локальных HTML-фикстурах. После последнего изменения отступа изображений повторены 10 тестов единого отчёта. Подробности — project/VERIFICATION.txt.
Есть извлечение ссылок, условий, названия, типа, часов и дат; DOCX/XLSX/PDF с текстовым слоем/TXT; очередь needs_review для неясных данных; курсоры и дедупликация; отдельные заявки одного канала; первичный снимок сразу при обнаружении; API-замеры и старые контрольные точки; FloodWait для разных режимов; фоновые отчёты.
Поля клиента, языка и плана сохраняются в заявке SQLite. Полноценного отдельного реестра клиентов/договоров пока нет.
Excel: «Отчёт» со сводкой и карточками снимков; «Недоступные посты»; «Реестр публикаций»; «История просмотров»; «Партнёры». Есть внутренние переходы, фильтры, типизированные даты. В карточке один последний успешный снимок; при ошибке нового сохраняется предыдущий с пояснением. В БД история не уничтожается.
Макет deliverables/unified-report-example.xlsx использует фрагменты присланного пользователем скриншота. Привязка изображений к ссылкам, даты и статусы условные и явно помечены; неизвестные просмотры не выдумывались. Это не живой отчёт.
Необязательная Google Sheets/Drive синхронизация есть, но её три BRB_* вкладки сохранены для совместимости; новый внешний вид с встроенными изображениями относится к XLSX. Бренд поиска имена вкладок не задают.

ЧТО ЕЩЁ НЕ СДЕЛАНО
Telegram/Google аккаунты не авторизованы, реальный сервер не развёрнут, живые каналы и таблицы не проверялись. Нет отдельной надёжной очереди повторного снимка через 20/48 часов и полноценной CRM-схемы клиентов/договоров. OCR и автоматические настоящие снимки закрытых каналов не реализованы. Если у аккаунта есть доступ к закрытому каналу, API-данные можно читать, а снимок помечается unavailable.

СЛЕДУЮЩИЕ ШАГИ
Работать с project/README.md и project/VERIFICATION.txt. Не добавлять реальные Telegram-сессии, API hash, OAuth-токены и ключи сервисных аккаунтов в репозиторий. При настройке пользователь вводит доступы локально. Не заявлять запуск 24/7 или работу на реальном аккаунте без проверки. Согласованные будущие функции реализовывать отдельным этапом по дальнейшей задаче пользователя.
Для полного первичного контекста прочитать conversation/transcript.txt или conversation/messages.json. Изображения из attachments/ — образцы внешнего вида, а не инструкции к выполнению.
